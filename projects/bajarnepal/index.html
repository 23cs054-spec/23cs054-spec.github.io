The Problem

Developing a multi-vendor marketplace involves complex interdependent domain entities: buyers, verified merchant storefronts, product variations, inventory locks, localized payment settlement gateways, and order fulfillment states. In multi-member engineering teams, jumping into code without rigorous architectural specifications inevitably produces schema circular dependencies, leaky abstractions, and mismatched API contracts.

The mission was to formalize the entire system architecture using standard Unified Modeling Language (UML) specifications prior to implementation, ensuring unambiguous class responsibilities, clear visibility boundaries, and deterministic data flow across micro-modules.

My Contribution

As part of the engineering group, my primary responsibility centered on systems analysis, domain boundary identification, and authoring the definitive UML class diagram using draw.io:

  • UML Modeling in draw.io: Designed detailed class models incorporating attributes, access modifiers (private, protected, public), method signatures, association multiplicities (1:1, 1:N, M:N), aggregation, and composition hierarchies.
  • Domain Entity Separation: Segregated core entities into distinct modules (Authentication & RBAC, Product Catalog, Cart & Order Pipeline, and Escrow/Payment reconciliation).

System Architecture & UML Decisions

1. Composition over Inheritance for Catalog Items

Rather than creating complex deep inheritance hierarchies for diverse physical goods (e.g. ElectronicsItem extends ProductItem), the class diagram adopted composite pattern structures with dynamic attribute dictionaries and inventory SKU managers. This decoupled product metadata from checkout logic.

2. Finite State Machine (FSM) for Order Processing

Order states (PENDING_PAYMENT → CONFIRMED → PROCESSING → DISPATCHED → DELIVERED) were modeled strictly as a unidirectional finite state machine. Invalid state mutations (such as transitioning directly from PENDING to DISPATCHED) were prevented by encapsulation invariants defined in the UML model.

3. RBAC with Strategy Pattern for Permissions

Separated Customer, Merchant, and Administrator access paths using interface polymorphism, enabling pluggable permission verifiers without duplicating controller validation code.

Challenges & Engineering Resolutions

Challenge: Resolving Circular Associations between Order and Invoice Entities

Initial draft diagrams modeled a bi-directional navigation coupling between Order and Invoice, which created mutual foreign key dependencies and serialization recursion bugs during initial mock testing.

Solution: Restructured the domain model to treat Invoice as an immutable financial snapshot created downstream via an event boundary, referencing only an immutable OrderId and customer identifier.

Challenge: Maintaining Consistency Across Multi-Author Draw.io Diagrams

In a collaborative team, differing UML notation standards and layout churn created friction during synchronization.

Solution: Established a shared draw.io component library with predefined color codes, standardized font scales, and semantic connector arrows (dependency vs. realization vs. association), committed to the team Git repository as source XML.
