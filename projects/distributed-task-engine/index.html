Distributed Task Engine

An asynchronous background job orchestrator featuring Redis Streams, worker pool auto-recovery, and real-time WebSocket state streaming.

The Problem

Synchronous HTTP request-response loops collapse under CPU-heavy or I/O-intensive workloads (such as image transformation, batch PDF report compilation, and mass transactional notifications). When web servers handle these operations in-band, connection pools starve, latency degrades exponentially, and single-point process crashes lead to cascading data corruption.

The goal of this system was to engineer a fault-tolerant, horizontally scalable asynchronous job dispatcher capable of queueing thousands of tasks with consumer group acknowledgment guarantees, automatic zombie worker detection, and live status dissemination.

My Role & Implementation

I designed and built the complete system from scratch using TypeScript and Node.js:

  • Engineered producer and consumer worker processes decoupled by an in-memory Redis message broker with persistence enabled via Append-Only File (AOF).
  • Implemented Redis Stream Consumer Groups (XREADGROUP, XACK, XPENDING, XCLAIM) to ensure at-least-once message delivery without task loss.
  • Created an automated Dead-Letter Queue (DLQ) with jittered exponential backoff retries for failed tasks.
  • Constructed a lightweight WebSocket telemetry gateway broadcasting queue depth, throughput metrics, and worker node health in real-time.
  • Containerized worker nodes and Redis using Docker Compose for isolated multi-container testing.

System Architecture & Technical Decisions

1. Redis Streams vs. Simple Redis Lists or Pub/Sub

Redis Pub/Sub offers fire-and-forget delivery without message durability or persistence. Simple LPUSH/RPOP lists lack consumer group offsets and failure acknowledgment mechanisms. Redis Streams provided the ideal trade-off: sub-millisecond memory speed combined with durable consumer group states and explicit XACK processing.

2. Zombie Worker Auto-Recovery via XCLAIM & Heartbeats

If a worker process terminates mid-execution (e.g. out-of-memory exception or network partition), the assigned task remains in the Pending Entries List (PEL). A supervisor thread polls XPENDING at regular intervals; any task idling past a configurable threshold (e.g., 30 seconds) is automatically claimed (XCLAIM) by an active worker node.

3. Non-Blocking Event Loops with Worker Threads

CPU-intensive tasks (cryptographic hashing, compression) were offloaded to Node.js worker_threads, keeping the primary event loop completely responsive to new incoming HTTP enqueue requests.

Challenges & Engineering Solutions

Challenge: Thundering Herd on Redis Stream Polling

When multiple worker consumers called blocking reads simultaneously with low timeouts, CPU spikes occurred on the Redis instance whenever new messages arrived in bursts.

Solution: Configured blocking stream reads (XREADGROUP BLOCK 2000) with consumer-level random backoff delays, smoothing out the request distribution and cutting broker CPU utilization drastically.

Challenge: Graceful Shutdown under SIGINT / SIGTERM

Abrupt container shutdowns previously interrupted active jobs mid-write, creating orphaned states in downstream storage.

Solution: Implemented a POSIX signal trap that stops accepting new tasks from Redis, gives active worker threads a 10-second grace window to complete in-flight transactions, and commits the final XACK before closing process sockets.
